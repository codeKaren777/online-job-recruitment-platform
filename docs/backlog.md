# Requirements-to-module implementation backlog

All items below are **planned, not implemented**. SRS refers to the supplied Version 1.0 markdown; Architecture refers to the fully reviewed Software Architecture Document. D identifiers are decisions in `decisions.md`. Acceptance requires automated positive, negative and ownership tests plus PostgreSQL integration tests where persistence is involved.

| ID / module | Requirement and source | Acceptance criteria | Dependencies |
| --- | --- | --- | --- |
| AUTH-1 / auth | Seeker/employer registration and roles. SRS §§2.4.1.1, 2.4.1.3, 2.2; Architecture §§5.1, 9.2-9.3 | Valid registration creates JOB_SEEKER or EMPLOYER with a hashed password. Reject ADMIN, unknown roles and attempts to inject privileged/account-state fields. Enforce agreed identifier uniqueness in service and database, including concurrent registrations. Never return password hashes. Invalid input creates no account. | D8 |
| AUTH-2 / auth + security | Login/logout for all three roles. SRS §2.4.1.2 and §2.5.1; Architecture §§5.1, 9.1 | Correct credentials for each allowed account produce a bounded-life token; bad credentials fail without disclosing account existence. Validate signature/algorithm, issuer, audience, expiry, subject and account state. Map only known roles from trusted identity. Missing/invalid tokens get 401, insufficient role 403. Logout follows agreed revocation scope; test token reuse after logout, expiry, removal and key rotation. Do not mistake Spring's disabled default logout for implementation. | AUTH-1, AUTH-3, D1, D3/D4 policies |
| AUTH-3 / auth + admin | Administrator provisioning. SRS §§2.2, 2.4.1, 2.4.7; Architecture §§5.1/5.5 | Controlled provisioning creates an ADMIN without any public registration path, default password or plaintext secret logs. Provisioning is repeat-safe and cannot silently promote an existing unrelated user. Test recovery/last-admin policy and normal admin login/logout. | D2 |
| PROFILE-1 / profile | Own profile creation/update/view. SRS §§2.4.2.1, 2.2; Architecture §5.2 | A seeker creates at most one profile and can read/update their own agreed fields. Identity is taken from authentication, not writable owner IDs. Another seeker/employer cannot change it. Validate inputs and preserve unrelated data. | AUTH-2, D10 |
| PROFILE-2 / profile | CV and supporting documents. SRS §§2.4.2.2, 2.4.5.3, 2.4.6.1; Architecture §§5.2, 13.3 | Owner uploads accepted formats/sizes; reject oversize, disallowed content, path traversal and unsafe filenames. Persist private metadata with reliable storage failure handling. No direct public file URLs. Owner access and application-authorized employer access are tested; unrelated users cannot enumerate/download documents. Apply agreed retention, replacement/snapshot and removal rules. | PROFILE-1, D6 |
| JOB-1 / job | Employer creates posts with requirements/deadline and views own posts. SRS §2.4.3, §2.5.3; Architecture §5.3 | Only EMPLOYER can create; server binds employer identity. Persist title, description, requirements and validated deadline. Own-post listing contains only that employer's posts. Reject invalid fields/deadlines under agreed rules. No unsupported editing/deletion workflow is inferred. | AUTH-2, D5 |
| JOB-2 / job | Browse, search, details, active/expired filtering. SRS §§2.1, 2.4.4; Architecture §§5.3, 8.1 | Show requirements and closing dates. Search matches agreed fields and combines with active/expired filter. Test just before, exactly at and after deadline with a fixed Clock; listing/details/application eligibility agree. Enforce agreed public/authenticated access, bounded pagination and deterministic ordering. No additional product filters presumed. | JOB-1, D5, D9 |
| APP-1 / application | Apply once to active jobs; initial PENDING; share applicant profile/documents. SRS §2.4.5, §2.5.2, §4; Architecture §§5.4, 7.4 | Only JOB_SEEKER applies using their authenticated identity. Reject expired/missing jobs and unmet agreed prerequisites. New application is PENDING; client cannot choose status/owner. Service checks duplicates and migration adds UNIQUE(job_id, job_seeker_id); concurrent duplicate submissions create exactly one row and return a controlled conflict for the loser. Use foreign keys and a transaction. Employer gains access only through their job/application relationship, following document snapshot policy. | PROFILE-1/2, JOB-1, D5/D6/D10 |
| APP-2 / application + profile | Employer reviews own applications and documents. SRS §2.4.6.1, §2.5.4, §4; Architecture §§5.4, 13.4 | Owning employer can list applications and view associated profile/documents. Changing job/application/document IDs cannot expose another employer's applicants. Apply ownership checks to both metadata and download paths; job seekers cannot list other applicants. Use agreed document retention/access lifecycle. | APP-1, D6 |
| APP-3 / application | Shortlist/reject applicants. SRS §2.4.6.2, §2.5.4; Architecture §5.4 | Owning employer can execute only approved transitions among PENDING, SHORTLISTED, REJECTED. Enforce enum/check constraint, service transition rules and concurrency protection. Reject unknown statuses, disallowed reversals and non-owner/non-employer requests. Persist accepted updates atomically. | APP-2, D7 |
| APP-4 / application | Seeker's own applications/statuses. SRS §2.4.6.3, §2.5.5; Architecture §5.4 | Seeker sees only their applications, linked job information and current status. Tests cover all three statuses and reflect employer updates. Forged seeker IDs cannot reveal other applicants. | APP-1/3 |
| ADMIN-1 / admin + auth | View users and verify where required. SRS §§2.4.7.1-2, 2.2; Architecture §5.5 | Only ADMIN lists registered users with safe DTOs (no credentials/tokens) and performs agreed verification changes. Auth-owned service persists state. Tests cover verification scope, repeat requests and agreed effects on login/actions. No email/SMS workflow added. | AUTH-3, D3 |
| ADMIN-2 / admin + auth/profile/job/application | Remove suspicious accounts. SRS §2.4.7.3; Architecture §5.5 | Only authorized ADMIN removes an account under agreed lifecycle policy. Enforce last-admin/self-removal policy, invalidate access as agreed and handle linked jobs/applications/documents without orphan disclosure. Tests cover repeat removal, already-issued JWTs and retention/cascade policy. | ADMIN-1, D4/D6 |
| NFR-1 / all | Privacy, responsiveness, clarity and availability. SRS §2.6; Architecture §11 | Security tests include role/ownership matrices and secret-safe errors/logging. Lists are bounded and tested for unnecessary queries. Verify database failure makes aggregate health unhealthy, migrations upgrade a populated previous schema, and persistent data survives container restart. Agree measurable load/availability targets before claiming compliance; frontend navigation/clarity is outside this backend foundation. | D11; throughout milestones |

## Milestones

1. **Next: identity and access.** Resolve D1-D4/D8, implement AUTH-1/2/3 with account migration, role enforcement and revocation tests. Open only the registration/login routes needed by that implementation; ADMIN is never a registration option.
2. Profiles/documents and job posts/search after D5/D6/D9/D10.
3. Transactional applications, ownership-limited review and status tracking after D7.
4. Administration lifecycle and cross-module privacy/reliability acceptance.

Email, SMS, notifications, interviews, microservices, frontend selection, extra statuses and unsupported product workflows are excluded. The backlog does not authorize those features.
