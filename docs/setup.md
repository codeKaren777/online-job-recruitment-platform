# Development Setup Guide

This guide explains how to set up and run the Online Job Recruitment Platform backend on your local machine.

The instructions are written for developers who want to understand what they are running before executing commands. **All terminal commands use Bash**, including on Windows through Git Bash.

## 1. Understand the Project First

Before running anything, open the project repository and identify the important files.

| File or directory | Purpose |
|---|---|
| `pom.xml` | Defines the Java dependencies and Maven build configuration. |
| `mvnw` | Runs Maven on Linux and macOS. It can also be used through Git Bash on Windows. |
| `mvnw.cmd` | Windows-specific Maven Wrapper script. Not needed for this guide. |
| `docker-compose.yml` or `compose.yaml` | Defines the services Docker Compose runs. |
| `.env.example` | Template showing the environment variables required by the project. |
| `.env` | Contains your local configuration and secrets. |
| `src/` | Contains the application source code and tests. |
| `target/` | Contains build outputs generated by Maven. |
| `docs/` | Contains project documentation, if present. |

The project uses:

- Java 21
- Spring Boot
- Maven Wrapper
- PostgreSQL 17
- Docker Compose
- Flyway database migrations
- JWT authentication

### Before continuing

Make sure you are working from the repository root. This is the directory containing `pom.xml`, the Maven Wrapper, and the Docker Compose configuration.

On Windows, open **Git Bash** from the project directory. On Linux, open your normal Bash-compatible terminal.

Run:

```bash
pwd
ls -la
```

`pwd` shows your current directory, while `ls -la` lists its contents, including hidden files such as `.env`.

If the expected project files are missing, navigate to the correct directory before continuing.

## 2. Install the Prerequisites

Install the following tools before setting up the application.

| Tool | Requirement |
|---|---|
| Git | Required to download and update the repository. |
| Java | JDK 21. |
| Docker | Docker Engine on Linux or Docker Desktop on Windows. |
| Docker Compose | Compose plugin or the Compose functionality included with Docker Desktop. |

Download Git for Windows from [git-scm.com](https://git-scm.com/download/win). Docker Desktop is available at [docker.com](https://www.docker.com/products/docker-desktop/).

Run the following commands in Bash:

```bash
git --version
java -version
docker version
docker compose version
```

Check that Java reports version 21 and that Docker can communicate with its running engine.

If `docker version` reports a connection error, start Docker Desktop on Windows or the Docker service on Linux before continuing.

## 3. Understand the Docker Setup

Before starting the application, understand the difference between a container, a service, and a volume.

- **Service:** A component defined in the Docker Compose configuration, such as the backend or database.
- **Container:** A running or stopped instance of a service.
- **Volume:** Storage managed by Docker that can preserve data after a container is removed.
- **Image:** The packaged files used to create a container.

The project is expected to have a PostgreSQL database service and a backend service. Confirm the actual names from the Compose configuration instead of assuming them.

### Inspect the available services

Run:

```bash
docker compose config --services
```

This lists the services defined in the Compose configuration.

For example, the output might contain:

```text
db
backend
```

Your actual output is authoritative. If the database service has a different name, use that name in subsequent commands.

### Inspect the configured volumes

Run:

```bash
docker compose config --volumes
```

This lists the named volumes declared by the Compose configuration.

To see Docker volumes that already exist on your machine, run:

```bash
docker volume ls
```

To inspect a particular volume, use its actual name:

```bash
docker volume inspect <volume-name>
```

Replace `<volume-name>` with the name shown by Docker. Do not type the angle brackets literally.

A PostgreSQL volume normally stores database files. It allows the database data to survive when containers are stopped or recreated.

**Important:** A configured volume does not necessarily mean that the volume already exists. Likewise, an existing Docker volume may belong to another project.

### Check what is already running

Run:

```bash
docker compose ps -a
```

This shows the containers associated with the current Compose project, including stopped containers.

If nothing is listed, the project may not have created any containers yet. That is normal during a fresh setup.

To see running containers across Docker projects, run:

```bash
docker ps
```

These checks help you avoid starting duplicate services or accidentally interfering with another project.

For private PDF storage, follow the [local MinIO and document-upload guide](minio-setup.md).
It explains each teammate's bucket, credentials, the reduced browser interface
and what can be tested while authentication is being developed.

## 4. Configure the Environment Variables

The application requires environment variables for PostgreSQL and JWT configuration.

Create or edit a file named `.env` in the **repository root**, alongside `pom.xml` and the Docker Compose configuration.

Use `.env.example` as the reference for the required variable names. This guide does not generate the file automatically.

Your `.env` should contain the following configuration:

```dotenv
POSTGRES_DB=recruitment
POSTGRES_USER=recruitment
POSTGRES_PASSWORD=your_local_database_password

DB_URL=jdbc:postgresql://localhost:5432/recruitment

JWT_SECRET_BASE64=your_base64_encoded_secret
JWT_ISSUER=groupcc2-recruitment
JWT_AUDIENCE=groupcc2-api
```

Replace the example password and secret with appropriate local values. Do not use the example values as production credentials.

### What each variable means

| Variable | Purpose |
|---|---|
| `POSTGRES_DB` | The database name PostgreSQL initializes when creating a new database instance. |
| `POSTGRES_USER` | The database username used during initial database creation. |
| `POSTGRES_PASSWORD` | The password associated with that database user. |
| `DB_URL` | The JDBC connection URL used by the backend to connect to PostgreSQL. |
| `JWT_SECRET_BASE64` | A Base64-encoded secret used for JWT operations. It should represent at least 32 cryptographically random bytes. |
| `JWT_ISSUER` | Identifies the issuer of the JWT tokens. |
| `JWT_AUDIENCE` | Identifies the intended audience of the JWT tokens. |

### Important database connection detail

The correct `DB_URL` depends on where the backend is running.

- **Backend running directly on your computer:** `localhost` normally points to the database port published by Docker.
- **Backend running inside Docker Compose:** The database hostname normally needs to be the database service name, such as `db`, rather than `localhost`.

Check `docker-compose.yml` or `compose.yaml` to see how `DB_URL` is configured for the backend. Compose may override the value from `.env`.

Do not change the URL blindly. Use the connection address appropriate for the way you intend to run the backend.

### JWT secret requirements

The JWT secret must be properly Base64-encoded and contain at least 32 random bytes. A short human-readable password is not sufficient.

Keep `.env` private. Never commit it to Git or share its contents in screenshots, logs, or public repositories. Confirm that `.env` is covered by `.gitignore`.

## 5. Validate the Configuration

Before starting the application, check whether Docker Compose can parse the configuration.

Run:

```bash
docker compose config --quiet
```

If the command completes without an error, Compose has accepted the configuration syntax.

This does not guarantee that the database will start successfully, that the credentials are correct, or that the backend can connect to PostgreSQL.

If validation fails, review:

- Whether the Compose file exists.
- Whether the `.env` file is in the repository root.
- Whether required environment variables are present.
- Whether the Compose configuration references variables that are missing or incorrectly named.

Do not proceed until you have resolved any configuration errors.

## 6. Start the Full Application

This is the recommended approach for normal development.

Starting the full stack allows Docker Compose to start the database and backend together. When the backend starts successfully, Flyway can execute the application's database migrations.

First, check your existing containers and volumes as described in Section 3.

Then run:

```bash
docker compose up --build -d
```

What this command does:

- `up` creates and starts the required services.
- `--build` builds or rebuilds images when necessary.
- `-d` runs the containers in the background.

Wait for the services to start. The first build may take several minutes.

### Check the running services

Run:

```bash
docker compose ps
```

Review the output to see whether the backend and database are running and whether their ports are published as expected.

A running container does not necessarily mean that its application is ready. Check the logs next.

### Check the backend logs

Run:

```bash
docker compose logs --tail 100 backend
```

Replace `backend` with the actual backend service name if the Compose configuration uses a different name.

Look for:

- Successful Spring Boot startup.
- Successful database connections.
- Flyway migration activity.
- Errors involving missing environment variables, authentication, ports, or database connectivity.

The backend is ready when the log contains messages like:

```text
Recruitment backend is ready and listening at http://localhost:8080
Backend health check: http://localhost:8080/actuator/health
```

The first startup can take longer while Docker builds the image and Spring Boot initializes Flyway, JPA, and the web server. Later starts should be faster when the image is already built.

To follow the logs continuously, run:

```bash
docker compose logs -f backend
```

Press `Ctrl+C` to stop following the logs. This does not stop the backend container.

### Check the health endpoint

If the application exposes Spring Boot Actuator's health endpoint, run:

```bash
curl -i http://localhost:8080/actuator/health
```

A healthy application normally returns HTTP `200` and a response containing `UP`.

If the endpoint returns an error, verify the backend logs and confirm that the health endpoint is enabled and accessible in the application's configuration.

### Default local addresses

| Component | Expected address |
|---|---|
| Backend API | `http://localhost:8080` |
| Health endpoint | `http://localhost:8080/actuator/health` |
| PostgreSQL | `localhost:5432`, if the database port is published |

These are expected local addresses, not guarantees. Confirm the actual port mappings using `docker compose ps`.

### Why the full stack matters

Starting only the database does not start Spring Boot and does not cause the backend to run Flyway migrations.

For the normal development setup, use:

```bash
docker compose up --build -d
```

This starts the configured stack, allowing the backend to initialize and apply pending migrations.

## 7. Run the Backend Directly on Your Computer

Use this option when you want to run Spring Boot from your terminal or IDE while PostgreSQL continues running in Docker.

First, start only the database service:

```bash
docker compose up -d db
```

Use the actual database service name discovered in Section 3 if it is not `db`.

Check that the database container is running:

```bash
docker compose ps
```

Review its logs if necessary:

```bash
docker compose logs --tail 100 db
```

The database must be accessible from your computer on the port configured in Compose.

### Load the environment variables

Bash does not automatically load variables from `.env`. From the repository root, use:

```bash
set -a
. ./.env
set +a
```

This loads the variables into the current Bash session so the application can read them.

Keep the variable names consistent with the application's Spring configuration. Also ensure that the `DB_URL` points to the database address accessible from your computer.

### Start Spring Boot

Run:

```bash
sh ./mvnw -B -ntp spring-boot:run
```

This uses the project's Maven Wrapper to start the application.

The backend runs in the foreground. Use `Ctrl+C` to stop it.

**Note:** This approach requires a compatible Java 21 installation. It also assumes that the application has been configured to read the required environment variables from the current process.

If you open a new terminal, load `.env` again before starting the backend.

## 8. Run Tests and Build the Application

The Maven Wrapper provides the main development and verification commands.

Run these commands from the repository root.

### Run the unit tests

```bash
sh ./mvnw -B -ntp test
```

This compiles the relevant code and runs the configured unit tests.

### Build the application package

```bash
sh ./mvnw -B -ntp package
```

This builds the application and creates its package in the `target/` directory.

The expected JAR file is:

```text
target/recruitment.jar
```

The exact filename depends on the artifact configuration in `pom.xml`.

### Run the full verification suite

```bash
sh ./mvnw -B -ntp verify
```

This runs the verification lifecycle, including the tests configured for the project.

If the project uses Testcontainers for integration tests, Docker must be running and accessible. These tests may start isolated containers rather than using the development database.

**Important:** Do not assume that every test uses the same database. Check the test configuration to determine whether it uses an isolated test database, an embedded database, or another configured service.

## 9. Stop the Application Safely

To stop the services managed by the current Compose project, run:

```bash
docker compose down
```

This stops and removes the Compose containers and associated network, but normally preserves named volumes.

When you start the project again, Docker can reuse the preserved database data.

### Understand the difference between these commands

| Command | Effect |
|---|---|
| `docker compose stop` | Stops the services without removing their containers. |
| `docker compose down` | Stops and removes the Compose containers and network. |
| `docker compose down -v` | Also removes Compose-managed named volumes and attached anonymous volumes. |

**Never use `docker compose down -v` as a routine cleanup command.** It can delete the database storage and permanently remove local development data.

Only use it when you intentionally want to reset the database and have confirmed that the data can be discarded.

## 10. Troubleshooting

### Docker cannot connect

Start Docker Desktop on Windows or the Docker service on Linux.

Verify connectivity with:

```bash
docker version
```

### The database port is already in use

Another PostgreSQL instance or container may already be using port `5432`.

Check:

```bash
docker compose ps
docker ps
```

Review the port mappings and identify the conflicting service before changing anything.

### The backend cannot connect to PostgreSQL

Check the following:

1. Confirm that the database container is running.
2. Check the database logs.
3. Verify `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`.
4. Verify the effective `DB_URL`.
5. Remember that `localhost` inside the backend container refers to that container itself, not the separate database container.

For a backend running inside Compose, use the database service name where appropriate. For a backend running directly on your computer, use the published host port.

### Database authentication fails after changing `.env`

PostgreSQL initialization variables are generally applied when the database is first initialized. Updating `.env` does not automatically change the password of a database user stored in an existing volume.

Confirm which credentials the existing database uses before making changes. Do not delete the volume simply to resolve an authentication problem unless you intentionally want to discard the stored data.

### The health endpoint does not respond

Check the service status:

```bash
docker compose ps
```

Then inspect the logs:

```bash
docker compose logs --tail 100 backend
```

Confirm that the backend is listening on the expected port and that the health endpoint is configured.

### Flyway migration errors

Inspect the backend logs for migration failures. Check that the database is reachable, the expected database is being used, and the migration files are available.

Do not manually delete migration history or database tables to bypass a migration failure. Determine the cause before modifying the schema.

### Maven tests fail

Confirm that Java 21 is installed:

```bash
java -version
```

Read the test output carefully. A failure may be caused by application code, missing environment variables, an unavailable dependency, or Docker not being accessible to Testcontainers.
