# Profile and document-upload endpoints

Base URL: http://localhost:8080. These five routes exist in ProfileController.
All require an active JOB_SEEKER acting on their own records. No request accepts
a userId or role to choose an owner.

**Current checkout:** SecurityConfig authorizes these routes only for
`JOB_SEEKER` tokens. Without a token expect 401; other roles expect 403.
Controller authorization and JWT-subject identity resolution are covered by
focused tests. Profile service operations still require the configured runtime
database and private storage integrations.

| Method | Endpoint | Input | Success after integration |
|---|---|---|---|
| PUT | /api/profile | JSON profile fields | 200, created/updated own profile |
| GET | /api/profile | None | 200, own profile; 404 if absent |
| POST | /api/profile/documents | multipart/form-data, part named file | 201, document metadata |
| GET | /api/profile/documents | None | 200, own document metadata array |
| GET | /api/profile/documents/{documentId}/download | None | 200, short-lived signed GET URL |
| DELETE | /api/profile/documents/{documentId} | Document UUID from upload/list | 204, empty body |

## Postman setup

Create an environment with baseUrl=http://localhost:8080, token=<JOB_SEEKER_TOKEN>
and documentId=<UUID_FROM_UPLOAD>. Set the collection authorization type to
Bearer Token with value {{token}}. Keep real tokens private.

For PUT, choose Body → raw → JSON. For POST upload, choose Body → form-data,
add key file, change its type from Text to File, and select your PDF. Let Postman
set the multipart Content-Type and boundary automatically.

## 1. Create or update your profile

PUT {{baseUrl}}/api/profile with Content-Type: application/json:

```json
{
  "displayName": "Test Applicant",
  "phone": "0123456789",
  "biography": "Backend development experience."
}
```

Display name is required/nonblank (max 200). Phone is optional (max 50), biography
optional (max 10000). PUT replaces optional fields; use null to clear them.

```bash
curl -i -X PUT http://localhost:8080/api/profile \
  -H 'Authorization: Bearer <JOB_SEEKER_TOKEN>' \
  -H 'Content-Type: application/json' \
  -d '{"displayName":"Test Applicant","phone":null,"biography":"Backend experience"}'
```

Expected response fields: displayName, phone, biography, createdAt, updatedAt.
Timestamps are generated by the server; entities and credentials are not returned.

## 2. Read your profile

```bash
curl -i http://localhost:8080/api/profile \
  -H 'Authorization: Bearer <JOB_SEEKER_TOKEN>'
```

Same response shape as PUT. Missing profile returns 404 instead of creating one.

## 3. Upload a PDF

Create your profile first. Use a real disposable PDF, maximum 5 MiB, a safe filename
like sample.pdf, extension .pdf, and MIME application/pdf. Empty/spoofed files,
traversal filenames and unsupported formats are rejected.

```bash
curl -i http://localhost:8080/api/profile/documents \
  -H 'Authorization: Bearer <JOB_SEEKER_TOKEN>' \
  -F 'file=@sample.pdf;type=application/pdf'
```

Expected 201 response shape (illustrative metadata only):

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "originalFilename": "sample.pdf",
  "contentType": "application/pdf",
  "byteSize": 12345,
  "createdAt": "2026-10-13T12:00:00Z"
}
```

Save the actual returned id as documentId. No storage key or public URL is returned.
The private bucket remains private throughout this workflow.

## 4. List your documents

```bash
curl -i http://localhost:8080/api/profile/documents \
  -H 'Authorization: Bearer <JOB_SEEKER_TOKEN>'
```

Expected 200 array of the same metadata objects; [] when an existing profile has
no documents. A missing profile returns 404.

## 5. Delete your own document

```bash
curl -i -X DELETE http://localhost:8080/api/profile/documents/<DOCUMENT_ID> \
  -H 'Authorization: Bearer <JOB_SEEKER_TOKEN>'
```

Expected 204 with no body. List again to confirm the metadata is gone. Another
seeker's document UUID or a missing document returns 404 after integration.
Storage failures can return 503 and require an owner retry, as described in
[the document module](profile-module.md#files-and-consistency).

## 6. Download your own document

```bash
curl -i http://localhost:8080/api/profile/documents/<DOCUMENT_ID>/download \
  -H 'Authorization: Bearer <TOKEN>'
```

The response contains a short-lived signed GET URL and its expiry timestamp.
The application verifies ownership before issuing the URL; the bucket remains
private and no permanent object URL is returned.

## Errors and negative endpoint tests

After the integration gate opens, check these cases with real tokens:

| Request | Expected |
|---|---|
| Missing/invalid/expired bearer token | 401 |
| EMPLOYER or ADMIN calls any own-profile route | 403 |
| SUSPENDED/REMOVED account | 403 |
| Blank displayName or oversized profile field | 400 INVALID_REQUEST |
| Empty/invalid PDF, wrong extension/MIME or unsafe filename | 400 INVALID_FILE |
| Upload beyond multipart limit | 413 FILE_TOO_LARGE |
| Missing profile or foreign/missing document ID | 404 NOT_FOUND |
| Storage/database service failure | Safe 503 code, no credentials/storage paths |

Security-filter errors need not use the controller's JSON error format. Application
errors use {"code":"..."}.

## Download and employer endpoints

There is currently **no employer-profile HTTP endpoint**. `downloadOwn` is
available at `/api/profile/documents/{documentId}/download`; it verifies
ownership before issuing a short-lived signed URL. `readForEmployer`,
`listForEmployer`, and `downloadForEmployer` remain service methods only.
Employer route contracts require the Jobs/Applications owner to supply real
specific-job/application authorization; download routes must be deliberately
registered and tested. The [contract-testing checklist](profile-contract-testing.md)
records this remaining work.

## What you can test before auth is ready

GET /actuator/health is available now for backend readiness:

```bash
curl --fail http://localhost:8080/actuator/health
```

Run `sh ./mvnw -B -ntp verify` for service behavior plus real private MinIO and
PostgreSQL component checks. For manual storage upload/signed-download/delete,
use the [MinIO walkthrough](minio-setup.md#7-test-while-authentication-is-being-developed).
Those checks do not exercise the full HTTP workflow above. Keep production
security in place while your teammate finishes authentication.
